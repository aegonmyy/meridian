+# Security
+
+This document covers who can do what, what the system guarantees hold regardless of who's acting, and what's honestly still unfinished. It's written for anyone deciding whether to trust this protocol with funds, or reviewing it for that decision on someone else's behalf. Audit status up front: none. This is unaudited, testnet software.
+
+## Trust model
+
+**What the owner can do.** Register and remove spokes (`addSpoke`, `removeSpoke`, `forceRemoveSpoke`), register and remove adapters on each spoke (`setAdapter`, `removeAdapter`), set the rebalancer address, rotate a spoke's hub pointer, tune the outbound gas limit, resolve quarantined spoke reports (`acceptQuarantinedReport`, `rejectQuarantinedReport`), and reconcile a specific, aged, dead in-transit leg by its exact tracked amount (`reconcileTransit`). All of these are single-owner calls with no timelock in v1, the tradeoff for that is discussed below. <!-- verified: HubAdminModule.sol (addSpoke, removeSpoke, forceRemoveSpoke, setRebalancer, reconcileTransit, acceptQuarantinedReport, rejectQuarantinedReport), SpokeAdminModule.sol (setAdapter, removeAdapter, setHub) -->
+
+**What the owner can no longer do.** There used to be a design for `adjustInTransitAssets`, letting the owner write `inTransitAssets` to any value with no evidence, no bound, and no delay, an unbounded write directly into a number that feeds share price. It was removed before shipping and replaced with `reconcileTransit`, which can only release a specific, already-tracked message id by its exact tracked amount, only after a seven day delay. Removing the unbounded setter is itself a security property worth stating plainly: there is no owner call anywhere in the current code that can move `totalAssets()` by an arbitrary amount. <!-- verified: HubAdminModule.sol:reconcileTransit is the only function that adjusts inTransitAssets outside the normal send/confirm flow, and it is bounded to a specific tracked amount -->
+
+**What the rebalancer and agent can do.** `HUB`'s capital-movement functions, `sendToSpoke`, `recallFromSpoke`, `rebalance`, are gated to the single `REBALANCER` address. `Rebalancer.sol` itself gates `proposeAllocation`, `rebalance`, and `recallFromSpoke` to `onlyAuthorized`, either the contract owner directly or the `AgentConsumer` contract. `AgentConsumer` in turn gates its own `proposeAllocation` forwarding to `onlyAgent`, either its own owner or a single designated `AGENT` wallet, the off-chain cron job's EOA. So an allocation proposal has to pass through two layers of access control before it reaches the hub, and every proposal is still checked against hard constraints (`AllocationMaths.validateAllocation`) regardless of who submitted it or how it was derived. <!-- verified: HubMessagingModule.sol (onlyRebalancer modifier on sendToSpoke, recallFromSpoke, rebalance), Rebalancer.sol:_onlyAuthorized, AgentConsumer.sol modifier onlyAgent -->
+
+**What a spoke is trusted with, and what bounds that trust.** A spoke is trusted to execute the instructions it receives and to report its own balance honestly, but that trust is bounded on both counts. `isValidSpoke` gates which addresses the hub will accept `_ccipReceive` calls from at all, an address has to be the currently registered spoke for its selector, not just any past registrant. A spoke's self-reported balance is never applied to `spokeBalances` directly, it passes through `_applyReportedBalance`'s upside-only sanity band first, anchored to `netSentToSpoke`, the hub's own ledger of what it has actually sent that spoke. See [docs/resilience.md](resilience.md) for the band's full mechanics. <!-- verified: HubAdminModule.sol:isValidSpoke, HubMessagingModule.sol:_applyReportedBalance -->
+
+**What CCIP is trusted with.** Message authenticity from a legitimate router is handled entirely by the inherited `CCIPReceiver` base contract, not reimplemented here. On top of that, both the hub and every spoke perform an explicit sender check, decoding `message.sender` and comparing it against the address they expect, hub checks against a registered spoke, spoke checks against its stored `HUB`. A message that passes the router check but comes from the wrong contract on the source chain still gets rejected.
+
+## Five invariants worth understanding on their own
+
+The invariant test suite (`test/invariants/hub/`, `test/invariants/spoke/`) fuzzes call sequences against the live contracts and checks many properties after every call, nineteen for the hub, nine for the spoke. Five of them are foundational enough to describe here in prose, each with a one-line note on how the suite enforces it.
+
+1. **The accounting identity.** `totalAssets() == idle balance + inTransitAssets + sum of spokeBalances`. This is the identity the whole fund location model in [docs/architecture.md](architecture.md) rests on. `invariant_accountingIdentity` checks it directly against live contract state after every fuzzed call sequence. <!-- verified: test/invariants/hub/hubInvariant.sol:invariant_accountingIdentity -->
+2. **Reservations track live pending withdrawals exactly.** `reservedAssets` equals the sum of `reservedIdle` across every withdrawal still pending, and the hub's own escrowed share balance equals the sum of shares across those same live entries. Two paired invariants check this, `invariant_reservedAssetsEqualsSumOfPendingReservedIdle` and `invariant_hubShareBalanceEqualsSumOfPendingShares`. <!-- verified: test/invariants/hub/hubInvariant.sol:invariant_reservedAssetsEqualsSumOfPendingReservedIdle, test/invariants/hub/hubInvariant.sol:invariant_hubShareBalanceEqualsSumOfPendingShares -->
+3. **In-transit tracking never desyncs.** `inTransitAssets` never exceeds `totalAssets()`, and in the invariant harness (where CCIP delivery is synchronous within the same call that sends a message) it fully reconciles back to zero between fuzzed calls, since every confirm lands before the next call in the sequence begins. A nonzero residual here would mean a leg's tracked amount was never released. <!-- verified: test/invariants/hub/hubInvariant.sol:invariant_inTransitAssetsBounded, test/invariants/hub/hubInvariant.sol:invariant_inTransitAssetsFullyReconciledBetweenCalls -->
+4. **Share price never drops below the 1:1 floor.** `convertToAssets(1e6)` never falls below `1e6 - 1` (one unit of rounding tolerance). This doesn't mean share price never fluctuates, yield and loss both move it, it means the vault never prices a share at less than the underlying asset it represents. <!-- verified: test/invariants/hub/hubInvariant.sol:invariant_sharePriceNeverDrops -->
+5. **Every share is accounted for.** The hub's own escrowed balance plus every tracked depositor's balance sums to exactly `totalSupply()`. Shares in escrow during a pending withdrawal are explicitly included, they're not burned until settlement, so they still count. <!-- verified: test/invariants/hub/hubInvariant.sol:invariant_sumOfSharesEqualsTotalSupply -->
+
+The remaining fourteen hub invariants and nine spoke invariants cover narrower properties, registry consistency, monotonic array growth, timestamp sanity, and are worth reading directly in the test files rather than restating here.

+## Known limitations
+
+| Limitation | Status |
+|---|---|
+| No owner-initiated manual pause, no separation between an automatic quarantine pause and a manual one | Open, deferred to v1.1. `_pause()`/`_unpause()` are today only ever called automatically from inside the sanity band logic, there is no owner entry point to pause or unpause outside that flow. <!-- verified: HubMessagingModule.sol:_applyReportedBalance is the only caller of _pause()/_unpause() anywhere in the Hub modules --> |
+| `proposeAllocation` sizing semantics | Settled, not open. Allocations are sized as bps of `totalAssets()`, with a separate pre-check against currently unreserved idle that fails the whole proposal atomically before any CCIP send if it wouldn't actually fit. <!-- verified: Rebalancer.sol:proposeAllocation --> |
+| Single asset assumption | Accepted for v1. `ASSET` is one immutable `IERC20` per spoke, USDC in practice. Multi-asset support would need each adapter to own its own token handling rather than the spoke assuming one asset throughout. <!-- verified: SpokeStorage.sol:ASSET --> |
+| Preview functions don't reflect async settlement | Accepted for v1. `previewRedeem`/`previewWithdraw` are unmodified ERC4626, computed as though redemption is always instant. Once a withdrawal actually routes through Path 2 or Path 3, the eventual payout is repriced at settlement, not at the preview call, the same gap an ERC-7540 style async vault would model explicitly with separate request and claim semantics. Meridian doesn't implement ERC-7540, this is a plain ERC4626 vault with an async settlement path bolted underneath it. See [docs/withdrawals.md](withdrawals.md). <!-- verified: no override of previewWithdraw/previewRedeem/maxWithdraw/maxRedeem anywhere in src/hub/ --> |
+| Path 2 freshness is a global, not per-withdrawal, condition | Accepted for v1. `_allSpokesFresh()` requires every active spoke to have reported within `MAX_STALENESS`, not just the spokes relevant to a specific withdrawal. One spoke that stops reporting can stall every Path 2 withdrawal in the system, not only withdrawals that would have touched that spoke. <!-- verified: HubWithdrawalModule.sol:_allSpokesFresh, loops every active selector unconditionally --> |
+| No timelock on the adapter registry | Accepted for v1, carried over from the original design reasoning. `setAdapter` and `removeAdapter` are both instant owner calls. `removeAdapter` being instant is intentional, an emergency circuit breaker needs to act faster than a compromised protocol can be exploited further. The same instant-call property on `setAdapter` is the actual tradeoff, a compromised owner key could point an adapter slot at a malicious contract immediately. Production deployment should use a multisig owner, and a timelock specifically on `setAdapter` while keeping `removeAdapter` instant is worth considering, without reintroducing the same speed problem on the emergency path. <!-- verified: SpokeAdminModule.sol:setAdapter, SpokeAdminModule.sol:removeAdapter, both onlyOwner with no delay --> |
