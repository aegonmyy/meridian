# Design Decisions

This document is the design log: alternatives considered, rejected, and the reasoning behind each, organized by theme rather than by file. It is a modernized rewrite of the project's original notes (`state.md`), verified against the code as it stands rather than reconstructed from memory. The file-by-file audit underlying this document is available at `docs/design-history-audit.md`. This document specifies the reasoning behind each mechanism; [docs/architecture.md](architecture.md) is assumed as prior reading.

## Message protocol

Cross-chain communication uses one library, `CCIPHelpers`, and one struct, `CcipMessage`, ABI-encoded into every CCIP payload. It is implemented as a library rather than a contract by design: no state, no deployment, linked directly into the hub and every spoke. `abi.encode` was chosen over `abi.encodePacked` because packed encoding can produce hash collisions when concatenating dynamic types; `abi.encode` is unambiguous for structs at some additional gas cost. The decode function performs no validation; the caller is responsible for checking `messageType` before acting, which both `HUB` and `SpokeVault`'s `_ccipReceive` do. <!-- verified: CCIPHelpers.sol:CCIPHelpers, CCIPHelpers.sol:encode, CCIPHelpers.sol:decode -->

The message shape underwent one significant redesign. The original design carried a single `adapter` and `amount` field per message, requiring one CCIP send per adapter operation; a rebalance touching two markets on the same spoke, for example Aave and Compound on Arbitrum, required two separate sends, doubling fees and latency across two atomic operations instead of one. The shipped design batches operations: `CcipMessage.instructions` is an array of `AdapterInstructions`, so one send carries every adapter operation for a spoke within a single atomic CCIP execution. <!-- verified: CCIPHelpers.sol:CcipMessage, CCIPHelpers.sol:AdapterInstructions -->

A single `WITHDRAW` message type, previously disambiguated by whether its `targetAdapter` field was zero (cross-chain recall) or nonzero (intra-spoke rebalance), is now two dedicated message types: `REBALANCE` for moving capital between adapters on the same chain, and `WITHDRAW_AMOUNT` for returning funds to the hub. The rationale for the split is unchanged: the Rebalancer has adapter-level precision when executing an allocation change, while the hub has no adapter-level visibility when paying out a user withdrawal, tracking only aggregate spoke balances, and must request a total amount and allow the spoke to determine the source. Collapsing both into one message type would require either the hub to guess adapter sources unsafely, or the Rebalancer to lose precision it possesses. Separating them into two named types makes the distinction explicit rather than encoded in a flag. <!-- verified: CCIPHelpers.sol:MessageType (REBALANCE, WITHDRAW_AMOUNT as separate values), SpokeHandlersModule.sol:_handleRebalance, SpokeHandlersModule.sol:_handleWithdrawalWithAmount -->

One protocol-level decision postdates the original notes entirely: every message id is derived from a monotonic nonce folded into a hash, not from the message's content. The earlier content-derived approach carried a genuine failure mode: two operations in the same block with the same amount and receiver hashed to the same id, and one silently overwrote the other's in-transit bookkeeping. Including a strictly incrementing nonce in the hash preimage makes this collision structurally impossible rather than merely unlikely. See [docs/resilience.md](resilience.md) for the complete mechanism. <!-- verified: HubMessagingModule.sol:_newMessageId -->

## Allocation math

`AllocationMaths` validates proposed allocations with a 2D array, `allocations[chain][protocol]`, rather than a flat array with hardcoded per-chain index ranges. The 2D structure expresses the chain concentration check as a natural outer loop and scales to any number of chains or protocols without redeploying the library; a flat array with hardcoded chain boundaries would require a new deployment for each added chain or protocol. <!-- verified: AllocationMaths.sol:validateAllocation -->

Three bugs from development illustrate defects of a kind that recur easily. An early version of the nested validation loop incremented the outer index within the inner loop, an infinite loop caught in review before reaching testing. `shouldRebalance`'s APY comparison originally subtracted unconditionally, `optimalWeightedApy - currentWeightedApy`, which underflows and reverts whenever the current allocation exceeds the optimal one; the fix adds an early return when optimal does not strictly exceed current. The grand-total check for a fully allocated proposal originally used `grandTotal > 10_000`, which catches over-allocation but permits under-allocation to pass silently; the fix uses `!= 10_000`, requiring allocations to sum to exactly the whole. All three fixes remain in place. <!-- verified: AllocationMaths.sol:validateAllocation, AllocationMaths.sol:shouldRebalance -->

The constraints are unchanged: a 500 bps dust floor on any nonzero allocation, a 6,000 bps cap per market, an 8,000 bps cap per chain, and a total equal to exactly 10,000 bps. `validateSingleMove` adds one further constraint: no single allocation may convert to more than 30% of `totalAssets`, limiting the capital a single proposal may move.

The off-chain allocation process underwent its own revision. The initial design placed an LLM directly in the allocation-decision path with no independent validation, rejected because a model does not guarantee adherence to hard numerical constraints; if a fallback is required for invalid output, the validation math must exist regardless, so including the model in the critical path introduced a failure mode without eliminating any required work. The shipped design assigns allocation decisions to an LLM (currently Gemini, not the DeepSeek originally planned), including soft diversification judgment that resists encoding as deterministic math, while hard constraints are validated independently on-chain by `Rebalancer.proposeAllocation` regardless of the model's output. One element of the original plan is not present in the shipped script: no fallback to a deterministic optimizer exists if the model call fails, and the off-chain constraint-check function defined in `strategy.js` is never invoked; the on-chain check in `Rebalancer.sol` is the sole enforcement mechanism at present. <!-- verified: strategy.js:getGeminiAllocation, strategy.js:validateAllocation (defined, unused), Rebalancer.sol:proposeAllocation -->

## Spoke design

Spokes register adapters dynamically, `setAdapter(bytes32 protocolId, address adapter)`, rather than through hardcoded protocol constants requiring redeployment to extend. Combined with the 2D allocation math above, adding a new chain or protocol to an existing chain is entirely a configuration change: deploy the spoke, call `setAdapter` per protocol, register the spoke on the hub, and update the off-chain agent's market list. No contract code changes are required. <!-- verified: SpokeAdminModule.sol:setAdapter, HubAdminModule.sol:addSpoke -->

The adapter registry uses an `exists` flag as the source of truth rather than removing entries from the backing array. `removeAdapter` flips the flag, an O(1) operation rather than the O(n) cost of swap-and-pop, at the cost of an array that only grows. This is an acceptable tradeoff for a registry that is small by design, three to five protocols per spoke. `removeAdapter` being an instant, no-timelock owner call is intentional: an emergency circuit breaker must act faster than an active exploit. The matching property on `setAdapter`, also instant and no-timelock, constitutes a genuine risk: a compromised owner key could point an adapter at a malicious contract immediately. Production deployment should use a multisig owner and consider a timelock specifically on `setAdapter`, while keeping `removeAdapter` instant. <!-- verified: SpokeAdminModule.sol:removeAdapter, SpokeAdminModule.sol:setAdapter -->

Deposit validation at the spoke is deliberately limited: adapter existence and nonzero amount. Allocation-level constraints, the bps caps and dust floor, are validated upstream by the Rebalancer before a message is sent, so a deposit instruction arrives at a spoke with that validation already performed. Duplicating it at the spoke would be redundant rather than additionally safe. <!-- verified: SpokeHandlersModule.sol:_handleDeposit -->

A general observation from `SpokeStorage`'s constructor, not specific to this protocol: Solidity executes parent constructors before the child constructor body, so a parent that does not validate its own inputs, combined with a child that assumes the parent performs that validation, is a latent defect. `_router` is passed directly into `CCIPReceiver(_router)` ahead of the spoke's own zero-address checks; this is safe only because `CCIPReceiver` is confirmed to validate it internally. This should be verified, not assumed, for any inherited base contract. <!-- verified: SpokeStorage.sol constructor -->

The single asset assumption, `ASSET` is one immutable `IERC20`, USDC in practice, remains a deliberate v1 scope limitation. Multi-asset support would require each adapter to manage its own token handling rather than the spoke assuming one asset system-wide; this is deferred to a later version.

## Hub accounting

`totalAssets()` illustrates a decision reversed early in development, with the reversal persisting as the current design. The initial design anchored `totalAssets()` to a separately tracked `totalPrincipal`, the sum of deposits minus withdrawals, so that share price would not decrease during CCIP transit or from a stale spoke report. This preserved principal protection but broke ERC4626 composability: dashboards, aggregators, and other integrating protocols expect `totalAssets()` to reflect real managed value including yield, and `previewRedeem`/`previewWithdraw` function correctly for users only if it does. The reversal made `totalAssets()` return real managed value, idle plus in-transit plus every spoke's reported balance, standard ERC4626 behavior, at the cost that principal protection is no longer guaranteed at the accounting level: a spoke exploit now visibly reduces share price rather than being absorbed. `totalPrincipal` is not merely unused following this change; it has been removed from the codebase entirely. <!-- verified: HubWithdrawalModule.sol:totalAssets, HubWithdrawalModule.sol:_deposit doc comment noting totalPrincipal was removed as dead state -->

Yield socialization follows directly from this design: users hold shares against the vault's combined value across every chain and adapter, with no per-user or per-spoke attribution in hub state. A high-performing market benefits every shareholder, not only those allocated there, and a loss is socialized identically. This is the standard model for a pooled vault and applies here without modification. <!-- verified: HubStorage.sol, no per-user spoke-attribution state anywhere -->

`_idleBalance()` reads the hub's raw USDC balance without filtering, so a token transferred directly to the hub outside the normal deposit flow is included in `totalAssets()`, functioning as a proportional donation to existing shareholders with no recovery path for the sender. This is standard ERC4626 behavior and is accepted without modification. <!-- verified: HubWithdrawalModule.sol:_idleBalance -->

The concurrent withdrawal race motivates the existence of `reservedAssets`: absent it, two withdrawal requests in the same block could each independently observe sufficient idle to cover themselves, both be queued, and only one could actually be paid. `reservedAssets` is incremented when a withdrawal is queued against idle and decremented on settlement or cancellation, so idle available to a new request is always `idle - reservedAssets`, never the raw idle balance. This increment/decrement pattern is unchanged, now distributed across the three-path engine with per-entry `reservedIdle` tracking rather than one variable updated at each call site. <!-- verified: HubWithdrawalModule.sol:_withdraw, HubWithdrawalModule.sol:_attemptSettleWithdrawal -->

In-transit accounting must decrement by the exact amount sent, not by any value derived from a spoke's self-reported balance, since that report includes yield accrued during transit and would corrupt the ledger if used for the decrement. The mechanism, a per-message mapping from message id to the exact amount sent, is unchanged in principle and has gained one addition: a `TransitLeg` struct now also records the origin selector and send timestamp per message, added to support `reconcileTransit`'s age-gated recovery path. Neither requirement existed jointly in the original design, since the reconciliation problem had not yet been addressed. <!-- verified: HubStorage.sol:inTransitAmount, HubStorage.sol:transitLegs -->

## Withdrawal engine

The three-path shape (idle covers the request and spokes are fresh: settle immediately; idle covers the request but spokes are stale: queue and refresh; idle does not cover the request: recall from spokes) was present in the original design in essentially its current form. Settlement mechanics once a withdrawal is queued were rewritten in full.

The original design quoted a withdrawal's payout at request time and paid that amount when settlement eventually completed. Under a frozen quote in a system where settlement may take minutes, any share price movement in the interim, a loss report, a yield report, another user's recall draining idle, would be absorbed by every shareholder except the withdrawer whose price was fixed, creating an arbitrage opportunity against the gap between quote and settlement. The shipped engine reprices at claim time: the request-time number is retained only as a sizing reference for the recall, and the actual payout is `previewRedeem(shares)` recomputed at the moment settlement executes, tracking the same price observed by every other shareholder. See [docs/withdrawals.md](withdrawals.md) for a worked example with exact figures.

Recall planning changed from selecting a single spoke to a haircut-capped, multi-leg plan across every active spoke sorted by descending balance, and from an implicit combined design (a `WITHDRAW` interaction's confirm also carried a fresh balance report) to an explicit, fail-closed dry run: if the full shortfall cannot be planned across every spoke, the request reverts before any commitment, with no shares locked and no CCIP dispatched.

The placement of the settlement gates is the most significant structural decision in this rewrite. `attemptSettlement` is permissionless by design, allowing CCIP callbacks to advance a stuck withdrawal without a settlement failure affecting a token-carrying execution. A permissionless settlement entry point also permits circumvention of path gating: calling it immediately after a stale-priced Path 2 withdrawal is queued, before any fresh report has landed. The resolution places every gate, freshness, leg completion, solvency, inside `_attemptSettleWithdrawal` rather than at any individual call site, so the same checks apply regardless of caller. <!-- verified: HubWithdrawalModule.sol:attemptSettlement, HubWithdrawalModule.sol:_attemptSettleWithdrawal -->

`_deposit` and `_withdraw` are the only ERC4626 hooks overridden; the public-facing `deposit`/`withdraw`/`redeem` pair is never overridden directly, consistent with OpenZeppelin's guidance that overriding the public pair risks inconsistent behavior between them. `_withdraw` never calls `super`, because the standard implementation burns shares and transfers assets within a single call, and an asynchronous path cannot always perform both immediately, shares are burned only once funds are confirmed available, requiring the full flow to be implemented directly rather than composed on the default. <!-- verified: HubWithdrawalModule.sol:_deposit, HubWithdrawalModule.sol:_withdraw -->

## Hardening campaign

Two fix campaigns, designated internally WI-1 through WI-7 and FX-1 through FX-8, closed gaps between the original design and behavior required under adversarial and edge-case conditions. A subset of these merit description beyond a changelog entry.

The original plan for a `DEPOSIT` that becomes permanently stuck specified a generic Chainlink-style `retryFailedMessage`/`getFailedMessages` recovery pair. The shipped mechanism is narrower and more constrained: `reconcileTransit`, gated to the owner, scoped to one specific already-tracked message id, releasable only for its exact tracked amount, and only after a seven day delay. It replaced an intermediate design, `adjustInTransitAssets`, which permitted the owner to write `inTransitAssets` to an arbitrary value with no evidence, bound, or delay, an unbounded write directly into a value that determines share price. The removal of that intermediate design constitutes a security property of the current system: no owner call can move `totalAssets()` by an arbitrary amount. <!-- verified: HubAdminModule.sol:reconcileTransit -->

A spoke's self-reported balance is validated against an upside-only sanity band before acceptance, anchored to `netSentToSpoke`, the hub's own record of funds actually sent to that spoke, rather than any value the spoke claims. A report exceeding the band is not clamped to the ceiling and applied; clamping still applies a fabricated value, only a smaller one. The report is quarantined instead: `spokeBalances` remains unmodified, the vault pauses new deposits and withdrawal requests, and the owner must explicitly accept or reject the report. Acceptance rebases the band's baseline to the accepted value; without this rebase, the band is fixed and time-independent, and a spoke's genuine cumulative yield eventually exceeds a fixed percentage ceiling permanently, at which point every subsequent honest report would immediately re-quarantine, a pause-and-accept cycle that does not resolve. See [docs/resilience.md](resilience.md) for the complete mechanics. <!-- verified: HubMessagingModule.sol:_applyReportedBalance, HubAdminModule.sol:acceptQuarantinedReport -->

The defensive receiver pattern evolved from an earlier all-or-nothing design. A `DEPOSIT` originally required every instruction in a batch to succeed before the spoke would confirm receipt to the hub; one failed instruction produced no confirm at all, leaving the hub waiting indefinitely while valid deposits remained unconfirmed. The current design independently attempts each instruction, skips and emits an event for any failure, and always sends a truthful confirm regardless of how many instructions succeeded. `docs/revert-audit.md` provides the systematic version of this pattern: every revert reachable inside both `_ccipReceive` entry points, enumerated and classified.

One element of the original notes was never implemented: a 24 hour cooldown between rebalances, intended to render stale spoke reports irrelevant relative to the rebalance cycle. `Rebalancer.sol` contains no cooldown constant, no last-rebalance timestamp, and no rate limiting of any kind. Rebalance cadence, whatever governs it operationally, is not enforced on-chain.

## Modularization

Both `Hub.sol` and `Spoke.sol` originated as single large files and were split into a storage base and sibling logic modules, with storage layout, external selectors, and gas cost verified unchanged at every step. The mechanism that renders a multi-module split safe for state is centralizing every struct, state variable, and event in one storage base contract inherited directly by every module: since Solidity assigns storage slots by declaration order across the inheritance chain, a single owner of every declaration precludes any module from altering slot assignment.

The mechanism enabling this for logic is the hook pattern: three sibling modules that do not inherit one another occasionally require calls between them, and Solidity provides no visibility into a sibling's members unless declared in a shared ancestor. The storage base declares a bodiless `virtual` function for each case that crosses a module boundary; one module implements it with `override`, and any module requiring access does so through the shared, inherited declaration. This is a mechanical pattern rather than a design decision among alternatives, but it is the element of the shipped module architecture not evident from either module file examined independently. See [docs/architecture.md](architecture.md) for the specific hooks declared on each side.
