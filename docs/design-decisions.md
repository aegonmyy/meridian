# Design Decisions

This is the design log, what was considered, what got rejected and why, what broke during development and what that taught, organized by theme rather than by file. It's a modernized rewrite of the project's original notes (`state.md`), verified against the code as it stands today, not carried forward from memory. If you want the raw file-by-file audit that produced this document, see `docs/design-history-audit.md`. This document is for anyone who wants the reasoning behind a mechanism, not just the mechanism, read it after [docs/architecture.md](architecture.md).

## Message protocol

Cross-chain communication is one library, `CCIPHelpers`, and one struct, `CcipMessage`, ABI-encoded into every CCIP payload. It's a `library`, not a `contract`, on purpose, no state, no deployment, gets linked directly into the hub and every spoke. `abi.encode` was chosen over `abi.encodePacked` because packed encoding can produce hash collisions when concatenating dynamic types, `abi.encode` is unambiguous for structs even at some extra gas cost. The decode function performs no validation of its own, the caller is responsible for checking `messageType` before acting, and both `HUB` and `SpokeVault`'s `_ccipReceive` do exactly that. <!-- verified: CCIPHelpers.sol:CCIPHelpers, CCIPHelpers.sol:encode, CCIPHelpers.sol:decode -->

The message shape itself went through one significant redesign. The original had a single `adapter` and `amount` field per message, one CCIP send per adapter operation. That meant a rebalance touching two markets on the same spoke, Aave and Compound on Arbitrum, needed two separate sends, double the fees, double the latency, two atomic operations instead of one. The shipped design batches: `CcipMessage.instructions` is an array of `AdapterInstructions`, so one send can carry every adapter operation for a spoke in a single atomic CCIP execution. <!-- verified: CCIPHelpers.sol:CcipMessage, CCIPHelpers.sol:AdapterInstructions -->

What used to be a single `WITHDRAW` message type, disambiguated by whether its `targetAdapter` field was zero (cross-chain recall) or nonzero (intra-spoke rebalance), is now two dedicated message types, `REBALANCE` for moving capital between adapters on the same chain and `WITHDRAW_AMOUNT` for pulling funds back to the hub. The underlying reason for the split hasn't changed: the Rebalancer knows exactly which adapter to pull from when it's executing an allocation change, adapter-level precision matters there, but the hub has no adapter-level visibility when it's paying out a user withdrawal, it only tracks aggregate spoke balances, so that path has to ask the spoke for a total amount and let the spoke decide where it comes from. Collapsing both into one message type would have forced either the hub to guess adapter sources unsafely, or the Rebalancer to lose precision it actually has. Splitting them into two named types made the distinction explicit instead of encoded in a flag. <!-- verified: CCIPHelpers.sol:MessageType (REBALANCE, WITHDRAW_AMOUNT as separate values), SpokeHandlersModule.sol:_handleRebalance, SpokeHandlersModule.sol:_handleWithdrawalWithAmount -->

One protocol-level decision that postdates the original notes entirely: every message id is a monotonic nonce folded into a hash, not a hash of the message's content. The earlier content-derived approach had a real failure mode, two operations in the same block with the same amount and receiver hashed to the same id, and one silently overwrote the other's in-transit bookkeeping. Adding a strictly incrementing nonce to the hash preimage makes that collision structurally impossible, not just unlikely. See [docs/resilience.md](resilience.md) for the full story. <!-- verified: HubMessagingModule.sol:_newMessageId -->

## Allocation math

`AllocationMaths` validates proposed allocations with a 2D array, `allocations[chain][protocol]`, rather than a flat array with hardcoded index ranges per chain. The 2D structure makes the chain concentration check a natural outer loop and scales to any number of chains or protocols without redeploying the library, a flat array with hardcoded chain boundaries would need a new deployment every time a chain or protocol was added. <!-- verified: AllocationMaths.sol:validateAllocation -->

Three bugs from development are worth remembering because the fixes are exactly the kind of thing that's easy to reintroduce. An early version of the nested validation loop incremented the outer index in the inner loop, an infinite loop caught in review before it reached testing. `shouldRebalance`'s APY comparison originally subtracted unconditionally, `optimalWeightedApy - currentWeightedApy`, which underflows and reverts whenever the current allocation happens to be better, fixed with an early return when optimal doesn't strictly exceed current. And the grand-total check for a fully allocated proposal originally used `grandTotal > 10_000`, which catches over-allocation but silently lets under-allocation through, fixed to `!= 10_000`, allocations must sum to exactly the whole. All three fixes are still in place today. <!-- verified: AllocationMaths.sol:validateAllocation, AllocationMaths.sol:shouldRebalance -->

The constraints themselves are unchanged: a 500 bps dust floor on any nonzero allocation, a 6,000 bps cap per market, an 8,000 bps cap per chain, and the total must equal exactly 10,000 bps. `validateSingleMove` adds one more, no single allocation may convert to more than 30% of `totalAssets`, a guard against one bad proposal moving too much capital in a single operation.

The off-chain side of this went through its own revision. The very first design put an LLM directly in the allocation-decision path with no independent math check, rejected because a model doesn't guarantee hard numerical constraints, and if a fallback is needed for invalid output, the validation math exists regardless, so putting the model in the critical path added a failure mode without removing any work. The design that shipped puts an LLM (currently Gemini, not the DeepSeek originally planned) in charge of the allocation itself, including soft diversification judgment that's hard to encode as clean math, while the hard constraints are checked independently on-chain by `Rebalancer.proposeAllocation` regardless of what the model returns. One piece of the original plan didn't make it into the shipped script, though: there's no fallback to a deterministic optimizer if the model call fails, and the off-chain constraint-check function defined in `strategy.js` is never actually called, the on-chain check in `Rebalancer.sol` is the only real safety net today. <!-- verified: strategy.js:getGeminiAllocation, strategy.js:validateAllocation (defined, unused), Rebalancer.sol:proposeAllocation -->

## Spoke design

Spokes register adapters dynamically, `setAdapter(bytes32 protocolId, address adapter)`, rather than through hardcoded protocol constants that would need a redeployment to extend. Combined with the 2D allocation math above, adding a new chain or a new protocol on an existing chain is entirely a configuration change: deploy the spoke, call `setAdapter` per protocol, register the spoke on the hub, and point the off-chain agent's market list at it. No contract code changes. <!-- verified: SpokeAdminModule.sol:setAdapter, HubAdminModule.sol:addSpoke -->

The adapter registry itself uses an `exists` flag as the source of truth rather than removing entries from the backing array. `removeAdapter` just flips the flag, O(1) instead of the O(n) a swap-and-pop would cost, at the price of an array that only ever grows. That's an acceptable trade for a registry that's small by design, three to five protocols per spoke. `removeAdapter` being an instant, no-timelock owner call is intentional too, an emergency circuit breaker for a compromised protocol needs to act faster than the exploit does. The matching tradeoff on `setAdapter`, also instant and no-timelock, is more honestly a risk: a compromised owner key could point an adapter at a malicious contract immediately. Production deployment should run a multisig owner and consider a timelock on `setAdapter` specifically, while keeping `removeAdapter` instant. <!-- verified: SpokeAdminModule.sol:removeAdapter, SpokeAdminModule.sol:setAdapter -->

Deposit validation at the spoke is deliberately shallow: does the adapter exist, is the amount nonzero. Allocation-level constraints, the bps caps and dust floor, are validated upstream by the Rebalancer before a message ever gets sent, so by the time a deposit instruction lands at a spoke, that math has already run. Duplicating it at the spoke would be redundant, not safer. <!-- verified: SpokeHandlersModule.sol:_handleDeposit -->

One general lesson from `SpokeStorage`'s constructor is worth stating even though it isn't specific to this protocol: Solidity runs parent constructors before the child constructor body, so a parent that doesn't validate its own inputs, combined with a child that assumes the parent handles it, is a silent bug waiting to happen. `_router` here is passed straight into `CCIPReceiver(_router)` ahead of the spoke's own zero-address checks, and that's safe only because `CCIPReceiver` is known to validate it internally. Worth checking, not assuming, for any inherited base. <!-- verified: SpokeStorage.sol constructor -->

The single asset assumption, `ASSET` is one immutable `IERC20`, USDC in practice, remains a deliberate v1 scope limitation. Multi-asset support would need each adapter to own its own token handling rather than the spoke assuming one asset system-wide, deferred to a later version.

## Hub accounting

`totalAssets()` is a good example of a decision that got reversed once early on, and the reversal is the version that stuck. The very first design anchored `totalAssets()` to a separately tracked `totalPrincipal`, sum of deposits minus withdrawals, specifically so share price would never dip during CCIP transit or from a stale spoke report. It worked, but it broke ERC4626 composability: dashboards, aggregators, and other protocols integrating against a vault expect `totalAssets()` to reflect real managed value including yield, and `previewRedeem`/`previewWithdraw` only work correctly for users if it does. The reversal made `totalAssets()` return real managed value, idle plus in-transit plus every spoke's reported balance, standard ERC4626 behavior, at the honest cost that principal protection is no longer guaranteed at the math level, a spoke exploit now visibly drops share price rather than being absorbed silently. `totalPrincipal` isn't just unused after this, it's gone from the codebase entirely. <!-- verified: HubWithdrawalModule.sol:totalAssets, HubWithdrawalModule.sol:_deposit doc comment noting totalPrincipal was removed as dead state -->

Yield socialization follows directly from that: users hold shares against the vault's combined value across every chain and every adapter, there's no per-user or per-spoke attribution anywhere in hub state. A high-performing market benefits every shareholder, not just whoever happened to be allocated there, and a loss is socialized the same way. This is the standard mental model for a pooled vault, and it's the correct one here. <!-- verified: HubStorage.sol, no per-user spoke-attribution state anywhere -->

`_idleBalance()` reads the hub's raw USDC balance with no filtering, so a token sent directly to the hub outside the normal deposit flow gets picked up and folded into `totalAssets()`, effectively donated to existing shareholders proportionally, with no recovery path for the sender. This is standard ERC4626 behavior and is accepted as-is. <!-- verified: HubWithdrawalModule.sol:_idleBalance -->

The concurrent withdrawal race is the reason `reservedAssets` exists at all: without it, two withdrawal requests in the same block could each independently see enough idle to cover themselves, both get queued, and only one could actually be paid. `reservedAssets` gets incremented the moment a withdrawal is queued against idle and decremented on settlement or cancellation, so idle available to any new request is always `idle - reservedAssets`, never the raw idle balance. That exact increment/decrement pattern is still how it works today, now spread across the three-path engine with per-entry `reservedIdle` tracking rather than one variable touched inline everywhere it used to be. <!-- verified: HubWithdrawalModule.sol:_withdraw, HubWithdrawalModule.sol:_attemptSettleWithdrawal -->

In-transit accounting needs to decrement by the exact amount sent, not by anything derived from a spoke's self-reported balance, because that report includes yield accrued during the transit window and would silently corrupt the ledger if used for the decrement. The mechanism for this, a per-message mapping from message id to the exact amount sent, is unchanged in spirit and has grown one companion since: alongside the amount, a `TransitLeg` struct now also records the origin selector and send timestamp per message, added specifically to support `reconcileTransit`'s age-gated recovery path. Neither piece existed as a joint requirement in the original design, the reconciliation problem hadn't been solved yet. <!-- verified: HubStorage.sol:inTransitAmount, HubStorage.sol:transitLegs -->

## The withdrawal engine

The three-path shape, idle covers it and spokes are fresh settle now, idle covers it but spokes are stale queue and refresh, idle doesn't cover it recall from a spoke, was present in the original design almost exactly as it exists today. What got rewritten wholesale is everything about how settlement actually happens once a withdrawal is queued.

The original design quoted a withdrawal's payout at request time and paid that number whenever settlement eventually completed. The problem with a frozen quote in a system where settlement can take minutes is that anything moving share price in between, a loss report, a yield report, another user's recall draining idle, gets absorbed by everyone except the withdrawer whose price was locked in, which is exactly backwards, and it's a standing invitation to game the gap between quote and settlement. The engine that shipped reprices at claim time: the request-time number is kept only as a reference for sizing the recall, and the actual payout is `previewRedeem(shares)` recomputed fresh at the moment settlement runs, tracking the same price every other shareholder sees. See [docs/withdrawals.md](withdrawals.md) for a worked example with exact numbers.

Recall planning changed from picking one spoke to a haircut-capped, multi-leg plan across every active spoke sorted by descending balance, and from an implicit two-birds-one-stone design (a `WITHDRAW` interaction's confirm happened to carry a fresh balance report too) to an explicit, fail-closed dry run: if the full shortfall can't be planned even across every spoke, the whole request reverts before anything is committed, no shares locked, no CCIP dispatched.

The most important structural decision in this rewrite, and one worth calling out on its own, is where the settlement gates live. `attemptSettlement` is permissionless by design, so that CCIP callbacks can nudge a stuck withdrawal without ever letting a settlement failure poison a token-carrying execution. But a permissionless entry point into settlement is also a way to try to jump the queue, calling it the instant a stale-priced Path 2 withdrawal is queued, before any fresh report has landed. The fix was to move every gate, freshness, leg completion, solvency, inside `_attemptSettleWithdrawal` itself rather than at whichever call site happens to trigger it, so the same checks apply no matter who or what calls it. <!-- verified: HubWithdrawalModule.sol:attemptSettlement, HubWithdrawalModule.sol:_attemptSettleWithdrawal -->

`_deposit` and `_withdraw` are the only ERC4626 hooks overridden, never the public-facing `deposit`/`withdraw`/`redeem` pair directly, following OpenZeppelin's own guidance that overriding the public pair risks inconsistent behavior between them. `_withdraw` never calls `super`, because the standard implementation burns shares and transfers assets in the same breath, and an async path can't do both right away, shares are only burned once funds are confirmed available, so the full flow had to be owned directly rather than composed on top of the default. <!-- verified: HubWithdrawalModule.sol:_deposit, HubWithdrawalModule.sol:_withdraw -->

## The hardening campaign

Two fix campaigns, referred to internally as WI-1 through WI-7 and FX-1 through FX-8, closed gaps between the original design and what actually holds up under adversarial and edge-case scrutiny. A few of these are worth understanding on their own rather than just as changelog entries.

The original plan for a `DEPOSIT` that gets permanently stuck was a generic Chainlink-style `retryFailedMessage`/`getFailedMessages` recovery pair. What shipped instead is narrower and safer: `reconcileTransit`, gated to the owner, scoped to one specific already-tracked message id, releasable only for its exact tracked amount, and only after a seven day delay. It replaced an intermediate design, `adjustInTransitAssets`, that let the owner write `inTransitAssets` to any value with no evidence, no bound, and no delay, an unbounded write directly into a number that feeds share price. That intermediate design never should have shipped, and its removal is a real security property of the current system: no owner call anywhere can move `totalAssets()` by an arbitrary amount. <!-- verified: HubAdminModule.sol:reconcileTransit -->

A spoke's self-reported balance is now checked against an upside-only sanity band before being trusted, anchored to `netSentToSpoke`, the hub's own record of what it actually sent that spoke, not anything the spoke claims about itself. A report that breaches the band is never clamped down and applied, clamping is still applying a fabricated number, just a smaller one, it's quarantined instead: `spokeBalances` stays untouched, the vault pauses new deposits and withdrawal requests, and an owner has to explicitly accept or reject the report. Accepting rebases the band's baseline to the accepted value, without that rebase, the band is flat and time-blind, and a spoke's genuine cumulative yield eventually exceeds a fixed percentage ceiling permanently, at which point every subsequent honest report would immediately re-quarantine, a pause-and-accept loop that never actually resolves. See [docs/resilience.md](resilience.md) for the full mechanics. <!-- verified: HubMessagingModule.sol:_applyReportedBalance, HubAdminModule.sol:acceptQuarantinedReport -->

The defensive receiver pattern, evolved from an earlier all-or-nothing design. A `DEPOSIT` originally required every instruction in a batch to succeed before the spoke would confirm receipt back to the hub, one bad instruction meant no confirm at all, and the hub would be left waiting indefinitely while genuinely valid deposits sat unconfirmed. The fix independently attempts each instruction, skips and emits an event for anything that fails, and always sends a truthful confirm regardless of how many instructions in the batch actually succeeded. `docs/revert-audit.md` is the systematic version of this: every revert reachable inside both `_ccipReceive` entry points, enumerated and classified.

One idea from the original notes never made it into the code: a 24 hour cooldown between rebalances, meant to give stale spoke reports time to become irrelevant relative to the rebalance cycle. There's no cooldown constant, no last-rebalance timestamp, and no rate limiting of any kind in `Rebalancer.sol` today. Whatever governs rebalance cadence in practice, it isn't enforced on-chain.

## Modularization

Both `Hub.sol` and `Spoke.sol` started as single large files and were split into a storage base plus sibling logic modules, verified at every step to leave storage layout, external selectors, and gas cost unchanged. The mechanism that makes a multi-module split safe for state is centralizing every struct, state variable, and event in one storage base contract that every module inherits directly, since Solidity assigns storage slots by declaration order across the inheritance chain, one owner of every declaration means nothing can silently shift.

The mechanism that makes it work for *logic* is the hook pattern: three sibling modules that don't inherit each other still sometimes need to call into one another, and Solidity has no notion of "my sibling's function" unless it's declared somewhere both sides can see. The storage base declares a bodiless `virtual` function for exactly the cases where this crosses a module boundary, one module implements it with `override`, and any module that needs to call it does so through the shared, inherited declaration. This is a purely mechanical pattern, not a design decision with alternatives weighed, but it's the one piece of the shipped module architecture that isn't self-evident from reading either module file in isolation, so it's worth naming here. See [docs/architecture.md](architecture.md) for the specific hooks each side declares.
