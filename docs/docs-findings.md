# Documentation Findings

This is an escalation list, not a fix list. Everything below was found while verifying claims for the documentation set (D-0 through D-7) and is a discrepancy between what the code says about itself and what it actually does, or between documented behavior and shipped behavior. Nothing here has been changed, this is a docs-only effort with zero source changes. Someone with authority to touch source should decide what, if anything, to do with each item.

## 1. Two NatSpec comments describe a visibility change that the module split has made structurally impossible without a redesign

`HubStorage.sol`, on the `onlyRebalancer` modifier, and `HubMessagingModule.sol`, on `_requestAllBalanceReports`, both carry comments describing the function's `public`/`external` visibility as a temporary pattern intended to be tightened to `internal` before mainnet. That was written before the Hub/Spoke modularization. Both `_requestAllBalanceReports` and the 3-argument `recallFromSpoke` overload are now cross-module hooks: declared `virtual` in `HubStorage` and called via `this.functionName(...)` self-calls from `HubWithdrawalModule`, specifically because a self-call needs the callee to be externally visible for Solidity to route it as a fresh external call with a fresh `msg.sender`. Tightening either function to `internal` now isn't a cleanup task anymore, it would break the hook mechanism these functions are part of, unless the cross-module call pattern is redesigned to route the `msg.sender` change some other way. The comments should probably be updated to reflect that this is now a structural property of the module architecture, not a deferred cleanup. <!-- verified: HubStorage.sol onlyRebalancer modifier doc comment, HubMessagingModule.sol:_requestAllBalanceReports doc comment, HubMessagingModule.sol:recallFromSpoke (3-arg overload) called via this. from HubWithdrawalModule.sol:_withdraw -->

## 2. A cross-file NatSpec reference points at a contract name, not the module that actually owns the function post-split

`SpokeConfirmsModule.sol`'s comment on the CCIP `allowOutOfOrderExecution: false` choice says "see the matching NatSpec in HUB._sendToSpoke for the full finding." `_sendToSpoke` is implemented in `HubMessagingModule.sol`, not directly in `HUB` (`HUB` inherits it, so the reference isn't wrong exactly, just imprecise, since `HUB` is a real, valid way to refer to the composed contract). Worth tightening to `HubMessagingModule.sol:_sendToSpoke` for anyone trying to jump to the exact file. Low severity, this is a documentation-precision nit left over from the module split, not a functional issue. <!-- verified: SpokeConfirmsModule.sol, comment referencing HUB._sendToSpoke -->

## 3. The off-chain agent's own constraint validator is defined but never called

`strategy.js` defines a `validateAllocation` function that mirrors the on-chain hard constraints exactly, dust floor, per-market cap, per-chain cap, grand total. It's never invoked anywhere in the file, the script builds a proposal from the model's output and encodes it directly without running that check first. The only enforcement that actually happens today is on-chain, `Rebalancer.proposeAllocation` calling `AllocationMaths.validateAllocation`, which reverts the whole proposal rather than falling back to anything if the model's output is invalid. That's not unsafe by itself, the on-chain check is real and does its job, but the off-chain script reads as though it has a validation layer it doesn't actually exercise, and there's no fallback to a deterministic optimizer if the model call fails or returns garbage, unlike what the original design notes describe. Worth either wiring the existing function in or removing it so the script doesn't imply a check that isn't happening. <!-- verified: strategy.js:validateAllocation defined at the module level, no call site anywhere in the file; Rebalancer.sol:proposeAllocation is the only place AllocationMaths.validateAllocation actually runs -->

## 4. A described operational mitigation, a 24 hour cooldown between rebalances, doesn't exist in the contracts

The original design notes describe a 24 hour cooldown between rebalance operations as a deliberate mitigation for CCIP report staleness. There is no cooldown constant, no last-rebalance timestamp, and no rate-limiting logic of any kind in `Rebalancer.sol` today, `proposeAllocation` and `rebalance` can both be called as often as an authorized caller wants. This isn't presented as fact anywhere in the new docs (see `docs/design-decisions.md`), but it's worth flagging here directly in case the cooldown was intended to still exist and its absence is itself the bug, rather than a decision that was quietly dropped. <!-- verified: Rebalancer.sol, no `constant` timing guard, no timestamp-gated logic anywhere in the file -->

## Findings from live testnet validation

The items below were found while exercising the deployed contracts end to end on Sepolia and the three L2 testnets (deposit, cross-chain allocation, recall, and all three withdrawal paths under real Chainlink CCIP), rather than during the documentation pass above. Unlike the D-0 through D-7 items, some carry an applied source change, noted inline where present.

## 5. A Path 3 withdrawal can defer on the yield accrued during its own recall flight, and does not self-heal until idle arrives from elsewhere

A Path 3 recall sizes its legs against the request-time quote, `assets - idleFree` computed when the withdrawal is queued. Settlement pays the claim-time price, `previewRedeem(shares)` recomputed when `_attemptSettleWithdrawal` runs. When yield accrues on a spoke during the recall's round trip, typically tens of minutes on live CCIP, the claim-time payout exceeds what the recall pulled back, and that difference must come from free hub idle by design. In a vault running fully deployed with no idle buffer, that idle does not exist, so settlement observes `availableForThisEntry < payout`, emits `SettlementDeferred`, and the entry stays pending. It does not self-heal the way the other deferral causes do. The shortfall is a solvency gap against a payout that only grows as more yield accrues, rather than a stale report that will refresh or an outstanding leg that will arrive. Recovery requires idle to enter the hub from an unrelated source, a deposit, another recall, or the withdrawer cancelling after the 24 hour timeout. Reproduced on testnet: a 3 USDC Path 3 withdrawal repriced from 3.000008 to 3.000155 during flight and stayed deferred until a 0.5 USDC deposit supplied the covering idle, after which it settled. The generic solvency-deferral case is documented in `docs/withdrawals.md`; what is worth deciding on is whether a vault expected to run fully deployed should size Path 3 recalls against a claim-time estimate rather than the request-time quote, or whether a standing idle buffer should be an operational requirement. <!-- verified: HubWithdrawalModule.sol:_withdraw (shortfall = assets - idleFree, sized at request time), HubWithdrawalModule.sol:_attemptSettleWithdrawal (payout = previewRedeem(entry.shares); availableForThisEntry < payout emits SettlementDeferred and returns) -->

## 6. proposeAllocation sized sends against totalAssets while funding them from idle, so a re-allocation reverted whenever any capital was already deployed (fix applied)

`Rebalancer.proposeAllocation` computed each send as `proposedAllocations[i][j] * totalAssets / 10_000`, and because `validateAllocation` requires the allocation to sum to exactly 10,000 bps, every proposal therefore requested 100% of `totalAssets`. The sends are paid from unreserved idle, so a proposal only fit when the hub held the entire vault as idle. After any deployment, `totalAssets` exceeded idle by the amount sitting on the spokes, down to a few wei of yield left stranded after a recall, and `proposeAllocation` reverted `InsufficientIdleForProposal`. Depositing did not clear it, since idle and `totalAssets` rise together and the gap equals the deployed balance; the exact-sum rule forbids proposing less than the whole; and a balance report does not clear it either, since the stranded value is real capital in a spoke's adapter rather than a stale number. The intended two-phase flow, recall everything to idle then re-propose, is defeated by a recall never fully draining a yield-bearing spoke. Reproduced on testnet: with 6 USDC idle and 0.000016 stranded across spokes, a full proposal reverted `InsufficientIdleForProposal(6000015, 6000000)`. A fix has since been applied and validated live: sends are now sized against deployable idle, `idle - reserved`, so a proposal deploys the chosen split of whatever is currently deployable and is unaffected by balances held on spokes, with a guard rejecting a proposal outright when nothing is deployable rather than firing zero-value sends. <!-- verified: Rebalancer.sol:proposeAllocation (sends sized against deployable = idleBalance() - reservedAssets; guard reverts when deployable == 0), test/regression/WI3_RebalancerRecallTest.t.sol:test_wi3_proposeAllocation_partlyDeployed_sizesAgainstIdle -->

## Findings from the permissionless factory migration

The items below carry applied source changes made to enable the permissionless self-serve factory model described in `agent-testing/FACTORY-PLAN-V2.md`. Each was implemented against the two product decisions locked on 2026-07-21, no managed off-chain agent per tenant, and fully caveat-emptor deposits, and each is validated by the test suite noted inline. No withdrawal-engine or accounting-core code was touched.

## 7. The Rebalancer had no ownership transfer and forced a mandatory AgentConsumer, both of which blocked a factory handoff (fix applied)

The Rebalancer stored `owner` as a bare `address public owner` set once in the constructor, with no `transferOwnership`, no setter, and nothing else, so whoever was passed at construction owned it forever, and its own NatSpec claimed the owner "can be transferred" while no such path existed. A factory has to own the Rebalancer while it wires the chain and protocol whitelists, then hand it to the tenant, so an immutable-in-practice owner was a hard blocker. The constructor also rejected a zero `_agentConsumer` and `_onlyAuthorized` treated `AGENT_CONSUMER` as a second authorized caller, but the locked decision is that there is no managed agent per tenant, so the owner must be the sole authorized caller with no AgentConsumer deployed at all. Both are now fixed: the Rebalancer inherits OZ `Ownable2Step`, so ownership moves in two steps, `transferOwnership` sets a pending owner and the new owner completes the handoff with `acceptOwnership`, which is the safe primitive for handing control to an anonymous tenant address since a mistyped or non-controllable address cannot brick the stack. Two-step, not plain `Ownable`, was chosen deliberately for exactly that reason. `AGENT_CONSUMER` stays immutable but may now be zero, and `_onlyAuthorized` authorizes the owner unconditionally and the AgentConsumer only when it is non-zero, so an unset consumer never matches an arbitrary caller. Making the consumer optional also removes the circular Rebalancer/AgentConsumer immutable dependency from the factory path entirely, so none of the CREATE2 or nonce-prediction machinery is needed. The constructor still reverts on a zero hub and, via `Ownable`, on a zero owner. <!-- verified: Rebalancer.sol:constructor (Ownable(_owner), reverts InvalidConstructorArguments only on zero hub, AGENT_CONSUMER may be zero), Rebalancer.sol:_onlyAuthorized (owner() always authorized, AGENT_CONSUMER authorized only when non-zero), test/units/rebalancer.t.sol:test_acceptOwnership_completesHandoff, test/units/rebalancer.t.sol:test_agentless_ownerAuthorized_randomRejected -->

## 8. Two factory contracts now deploy and hand off a tenant's stack in one transaction per chain (added)

`src/factory/HubFactory.sol` and `src/factory/SpokeFactory.sol` are the permissionless deployers, each holding the per-chain constants (router, LINK, USDC, and for the spoke factory the hub chain selector) as immutables so callers do not pass them. `HubFactory.createHub` deploys the Hub with the factory as interim owner and no rebalancer, deploys the Rebalancer with no AgentConsumer, sets the rebalancer on the hub, wires the caller's whitelists, optionally pulls LINK from the caller and forwards it to the hub, then begins the ownership handoff of both contracts to the caller and keeps no authority. `SpokeFactory.createSpoke` deploys the Spoke against an already-deployed hub, deploys and registers each adapter from an `AdapterSpec` designed to extend beyond Aave via a kind enum plus an encoded params blob, optionally funds LINK, and hands the spoke to the caller. Adapters are deployed per spoke because an Aave adapter holds the aToken itself and cannot be shared across tenants. The Hub and Spoke inherit plain OZ `Ownable`, so their `transferOwnership(msg.sender)` lands immediately, while the Rebalancer inherits `Ownable2Step`, so its handoff completes on the caller's `acceptOwnership`, and because both target `msg.sender`, a live caller transferring to itself, neither can be handed to an address that cannot act. Both factories expose `getHubsByOwner`/`getSpokesByOwner` and a global enumerable list, the due-diligence registry the open-deposit model relies on. A strictly additive `addSpokes(uint64[],address[])` was added to the Hub admin path as the return-trip batch helper, a thin owner-gated loop with a length-match check that inlines the exact per-entry logic of the existing `addSpoke`, which was left unchanged. <!-- verified: HubFactory.sol:createHub (Hub owner=this then transferOwnership(msg.sender), Rebalancer agentConsumer=address(0), setRebalancer, whitelist loops, LINK safeTransferFrom, registry writes), SpokeFactory.sol:createSpoke (SpokeVault deploy, _deployAdapter per AdapterSpec, setAdapter, transferOwnership(msg.sender)), HubAdminModule.sol:addSpokes (onlyOwner, MismatchedArrayLengths guard, per-entry logic identical to addSpoke), test/units/factory/FactoryTest.t.sol:test_createHub_factoryRetainsNoAuthority, test/units/factory/FactoryTest.t.sol:test_addSpokes_equivalentToSingleCalls -->
