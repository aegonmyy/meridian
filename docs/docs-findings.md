# Documentation Findings

This is an escalation list, not a fix list. Everything below was found while verifying claims for the documentation set (D-0 through D-7) and is a genuine discrepancy between what the code says about itself and what it actually does, or between documented behavior and shipped behavior. Nothing here has been changed, this is a docs-only effort with zero source changes. Someone with authority to touch source should decide what, if anything, to do with each item.

## 1. Two NatSpec comments describe a visibility change that the module split has made structurally impossible without a redesign

`HubStorage.sol`, on the `onlyRebalancer` modifier, and `HubMessagingModule.sol`, on `_requestAllBalanceReports`, both carry comments describing the function's `public`/`external` visibility as a temporary pattern intended to be tightened to `internal` before mainnet. That was written before the Hub/Spoke modularization. Both `_requestAllBalanceReports` and the 3-argument `recallFromSpoke` overload are now cross-module hooks: declared `virtual` in `HubStorage` and called via `this.functionName(...)` self-calls from `HubWithdrawalModule`, specifically because a self-call needs the callee to be externally visible for Solidity to route it as a fresh external call with a fresh `msg.sender`. Tightening either function to `internal` now isn't a cleanup task anymore, it would break the hook mechanism these functions are part of, unless the cross-module call pattern is redesigned to route the `msg.sender` change some other way. The comments should probably be updated to reflect that this is now a structural property of the module architecture, not a deferred cleanup. <!-- verified: HubStorage.sol onlyRebalancer modifier doc comment, HubMessagingModule.sol:_requestAllBalanceReports doc comment, HubMessagingModule.sol:recallFromSpoke (3-arg overload) called via this. from HubWithdrawalModule.sol:_withdraw -->

## 2. A cross-file NatSpec reference points at a contract name, not the module that actually owns the function post-split

`SpokeConfirmsModule.sol`'s comment on the CCIP `allowOutOfOrderExecution: false` choice says "see the matching NatSpec in HUB._sendToSpoke for the full finding." `_sendToSpoke` is implemented in `HubMessagingModule.sol`, not directly in `HUB` (`HUB` inherits it, so the reference isn't wrong exactly, just imprecise, since `HUB` is a real, valid way to refer to the composed contract). Worth tightening to `HubMessagingModule.sol:_sendToSpoke` for anyone trying to jump to the exact file. Low severity, this is a documentation-precision nit left over from the module split, not a functional issue. <!-- verified: SpokeConfirmsModule.sol, comment referencing HUB._sendToSpoke -->

## 3. The off-chain agent's own constraint validator is defined but never called

`strategy.js` defines a `validateAllocation` function that mirrors the on-chain hard constraints exactly, dust floor, per-market cap, per-chain cap, grand total. It's never invoked anywhere in the file, the script builds a proposal from the model's output and encodes it directly without running that check first. The only enforcement that actually happens today is on-chain, `Rebalancer.proposeAllocation` calling `AllocationMaths.validateAllocation`, which reverts the whole proposal rather than falling back to anything if the model's output is invalid. That's not unsafe by itself, the on-chain check is real and does its job, but the off-chain script reads as though it has a validation layer it doesn't actually exercise, and there's no fallback to a deterministic optimizer if the model call fails or returns garbage, unlike what the original design notes describe. Worth either wiring the existing function in or removing it so the script doesn't imply a check that isn't happening. <!-- verified: strategy.js:validateAllocation defined at the module level, no call site anywhere in the file; Rebalancer.sol:proposeAllocation is the only place AllocationMaths.validateAllocation actually runs -->

## 4. A described operational mitigation, a 24 hour cooldown between rebalances, doesn't exist in the contracts

The original design notes describe a 24 hour cooldown between rebalance operations as a deliberate mitigation for CCIP report staleness. There is no cooldown constant, no last-rebalance timestamp, and no rate-limiting logic of any kind in `Rebalancer.sol` today, `proposeAllocation` and `rebalance` can both be called as often as an authorized caller wants. This isn't presented as fact anywhere in the new docs (see `docs/design-decisions.md`), but it's worth flagging here directly in case the cooldown was intended to still exist and its absence is itself the bug, rather than a decision that was quietly dropped. <!-- verified: Rebalancer.sol, no `constant` timing guard, no timestamp-gated logic anywhere in the file -->
