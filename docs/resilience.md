# Resilience

This document is the failure design story. It's written for anyone who wants to understand why the code looks defensive in the places it does, rather than trusting happy-path CCIP delivery the way a naive first draft would. Read [docs/architecture.md](architecture.md) first for the message protocol these mechanisms all sit on top of.

Single-chain intuitions don't survive contact with cross-chain messaging. On one chain, a call either succeeds in this transaction or reverts and nothing happened. Across CCIP, a message can be sent and take twenty minutes to arrive, can arrive out of order relative to another message, can fail partway through execution on the destination chain and get stuck in a recoverable-but-not-automatic state, and, if you trust a spoke's self-reported data without checking it, can simply lie. Almost every non-obvious mechanism in this codebase is the answer to one of four questions about a message: what if it never arrives, what if it arrives twice, what if it arrives late, what if it arrives lying.

## Never arrives

A message that's stuck, not failed, just never executed or never even attempted, needs a way out that doesn't depend on CCIP fixing itself. Three separate mechanisms cover the three places this can happen.

**A pending withdrawal that never settles**, because a spoke stopped reporting or a recall leg never lands, gets `cancelWithdrawal` as a backstop. After `WITHDRAWAL_TIMEOUT` (24 hours), the withdrawal's own owner, and only that owner, can cancel it themselves and get their escrowed shares back. See [docs/withdrawals.md](withdrawals.md) for the full mechanics. <!-- verified: HubStorage.sol:WITHDRAWAL_TIMEOUT = 24 hours, HubWithdrawalModule.sol:cancelWithdrawal -->

**A `DEPOSIT` that's provably dead**, the spoke's `CONFIRM_RECEIPT` will never arrive because the message is permanently failed, gets `reconcileTransit`. This is a deliberately narrow tool, and it replaced something much more dangerous. The earlier design, `adjustInTransitAssets`, let the owner write `inTransitAssets` to any value with no evidence, no bound, and no delay, an unbounded write to a number that directly feeds share price. `reconcileTransit` can only release a *specific* tracked message id, by its *exact* tracked amount, and only after `TRANSIT_RECONCILE_DELAY` (7 days) has passed since it was sent. It can never invent value or inflate the vault, it can only write down exactly what's already known to be stuck. <!-- verified: HubAdminModule.sol:reconcileTransit, HubStorage.sol:TRANSIT_RECONCILE_DELAY = 7 days -->

The intended operational order is to attempt CCIP's own manual execution first, and only reach for `reconcileTransit` once the message is provably dead, confirmed permanent failure, manual execution exhausted. A late `CONFIRM_RECEIPT` arriving after reconciliation is harmless: the tracked amount is already deleted, so the arrival's decrement subtracts zero and only updates the spoke's balance.

**An outbound confirm that fails to send**, LINK exhausted, router hiccup, gets queued instead of reverting. `_sendOrQueueConfirm` wraps both `getFee` and `ccipSend` in `try`/`catch`. On any failure it persists a `PendingConfirm` record and emits `ConfirmSendFailed`, rather than reverting the whole handler and unwinding work that already happened (an adapter deposit, a balance update) along with it. The permissionless `retryConfirm` rebuilds the message fresh, spoke balance recomputed at retry time, never resent stale, and anyone can call it to unstick the queue. <!-- verified: SpokeConfirmsModule.sol:_sendOrQueueConfirm, SpokeConfirmsModule.sol:retryConfirm -->

## Arrives twice, or collides

Message identity in Meridian is a monotonic nonce, not a hash of the message's content. `_newMessageId` increments `_messageNonce` and folds it into a `keccak256` alongside the caller-supplied context, the chain id, and the hub's own address. <!-- verified: HubMessagingModule.sol:_newMessageId -->

The reason this matters is that content-derived ids collide. If two operations in the same block have the same amount and the same receiver, hashing only the content produces the same id for both, and one silently overwrites the other's bookkeeping, corrupting `inTransitAmount` tracking or clobbering a pending withdrawal entry. A strictly incrementing nonce as part of the preimage means two operations can never share an id, full stop, regardless of what else about them happens to match.

## Arrives late

A message that arrives after the state it was relevant to has already moved on needs to be recognized as stale, not misapplied to whatever is happening now.

The clearest example is a Path 3 recall leg's `CONFIRM_WITHDRAWAL` arriving after its withdrawal was already cancelled, or after that pending entry is otherwise gone. `legToWithdrawal[legId]` is set the moment a leg is dispatched and is deliberately **never deleted**, even after the withdrawal it belongs to settles or gets cancelled. If it were deleted, a late arrival for that leg id would fail to resolve back to any withdrawal at all, and would need to be treated as though it were something else entirely, specifically it could be mistaken for a fresh, unrelated Rebalancer-driven recall, the kind that has no `pendingWithdrawal` attached and whose arriving tokens should just become ordinary idle. Keeping the mapping populated forever means a late leg arrival always resolves to its true origin. The callback checks whether that withdrawal is still live (`shares > 0`); if not, the arrival is routed to the orphaned-arrival path, `OrphanedRecallArrival` fires, and the funds land as ordinary idle, correctly, instead of being silently misattributed to something it isn't. <!-- verified: HubStorage.sol:legToWithdrawal (never deleted by any function), HubMessagingModule.sol:_handleWithdrawalCallback -->

## Arrives lying

A spoke's self-reported balance is data from a contract Meridian doesn't fully trust to be honest, whether from a bug, a decoding error, or an actual compromise. `_applyReportedBalance` is the single choke point every balance-carrying callback routes through before writing anything to `spokeBalances`, and it checks the report against a band before accepting it. <!-- verified: HubMessagingModule.sol:_applyReportedBalance, called from all four callback handlers -->

The band is upside-only: `reported <= netSentToSpoke[selector] * (10,000 + MAX_YIELD_BPS) / 10,000 + REPORT_DUST`. `MAX_YIELD_BPS` is 2,000 (20%), `REPORT_DUST` is a flat 100e6 USDC to absorb rounding noise on small spokes. `netSentToSpoke` is the hub's own running ledger of what it has ever sent to that spoke via `DEPOSIT`, minus what's ever actually come back via `CONFIRM_WITHDRAWAL`, so the ceiling is anchored to something the hub tracked itself, not to anything the spoke claims. Under-reporting always passes, a lower number only deflates share price, the direction that's safe to trust without a check, though a drop steeper than `LOSS_ALERT_BPS` (5%) since the last report still fires an informational `SpokeBalanceDropped` event for visibility. <!-- verified: HubMessagingModule.sol:_applyReportedBalance, HubStorage.sol:MAX_YIELD_BPS = 2_000, HubStorage.sol:REPORT_DUST = 100e6, HubStorage.sol:LOSS_ALERT_BPS = 500 -->

On breach, the report is never clamped down to the ceiling and applied anyway. Clamping corrupts pricing in the safe direction just as surely as trusting the raw number corrupts it in the dangerous one, a clamped number is still a fabricated number. Instead the report is quarantined: `spokeBalances` is left completely untouched, the suspicious value is stored separately in `quarantinedReports`, `SuspiciousSpokeReport` fires, and the vault pauses, blocking new deposits and new withdrawal requests, until an owner resolves the quarantine one way or the other.

Resolution is either `acceptQuarantinedReport` or `rejectQuarantinedReport`. Rejecting discards the suspicious value and `spokeBalances` simply keeps whatever it last held. Accepting applies the value and, critically, rebases `netSentToSpoke` to match it. Without that rebase, the band is flat and time-blind by construction: a spoke's genuine cumulative yield eventually exceeds a fixed 20% ceiling permanently (roughly two years at 10% APY under the default band), and every honest report after that point would immediately re-quarantine again, a permanent pause-and-accept flap that never actually resolves. Accepting is meant to be an attestation with a durable effect, the owner has independently confirmed this balance is legitimate, so it becomes the new verified baseline the next report is measured against, not a one-time waiver that leaves the same ceiling in place to be hit again next cycle. <!-- verified: HubAdminModule.sol:acceptQuarantinedReport, HubAdminModule.sol:rejectQuarantinedReport -->

## The defensive receiver principle

One rule underlies most of the resilience work above and in the handlers that receive CCIP messages generally: never hard-revert the whole handler after tokens have already arrived or effects have already committed. A revert inside `_ccipReceive` unwinds the entire destination execution, including any token transfer that logically already happened in that call frame, which doesn't strand funds safely in the receiving contract, it strands the whole message in CCIP's failed-execution limbo, retryable only through manual intervention and permanently stuck if the failure condition is deterministic. So the pattern everywhere in the inbound handlers is: attempt each independent piece of work, catch failure at the smallest reasonable granularity, skip the failed piece and emit an event describing exactly what was skipped and why, and keep going.

**Worked example: a removed adapter.** Say the hub sends a `DEPOSIT` instructing the spoke to deploy 300 USDC into a protocol identified by `bytes32("AAVE")`, but that adapter was removed on the spoke (`exists == false`) sometime after the hub last synced its own view of the spoke's registry. A naive handler would either revert on the unknown adapter, stranding the entire `DEPOSIT`'s tokens, including any other instructions in the same batch, in CCIP limbo, or silently drop the funds. What actually happens: `_handleDeposit` checks `exists` per instruction inside its loop, skips the missing adapter, emits `DepositInstructionFailed(protocolId, 300e6, "adapter not found")`, and continues to the next instruction in the batch. The 300 USDC is never lost, it's already sitting in the spoke's own balance from the token transfer that preceded `_ccipReceive`, it just stays there as spoke idle instead of getting deployed. `_aggregatedSpokeBalance` counts idle alongside every active adapter's balance, so the hub's accounting stays exact, the funds show up in the next `CONFIRM_RECEIPT` either way, deployed or idle, nothing is stranded and nothing needs a separate recovery step. <!-- verified: SpokeHandlersModule.sol:_handleDeposit (the exists check and DepositInstructionFailed emission), SpokeHandlersModule.sol:_aggregatedSpokeBalance (idle plus active adapters) -->

[docs/revert-audit.md](revert-audit.md) is the systematic version of this principle, a full enumeration of every revert reachable inside both `_ccipReceive` entry points, classified as keep, convert to an event, or route to a reconciliation path, with the reasoning for each one.
