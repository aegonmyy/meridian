# Security

This document specifies the trust model, the invariants the system guarantees regardless of actor, and known limitations. It is intended for readers evaluating whether to trust this protocol with funds, or reviewing that decision on behalf of others. Audit status: none. This is unaudited, testnet software.

## Trust model

**Owner authority.** The owner may register and remove spokes (`addSpoke`, `removeSpoke`, `forceRemoveSpoke`), register and remove adapters on each spoke (`setAdapter`, `removeAdapter`), set the rebalancer address, rotate a spoke's hub pointer, tune the outbound gas limit, resolve quarantined spoke reports (`acceptQuarantinedReport`, `rejectQuarantinedReport`), and reconcile a specific, aged, dead in-transit leg by its exact tracked amount (`reconcileTransit`). All are single-owner calls with no timelock in v1; the associated tradeoff is discussed below. <!-- verified: HubAdminModule.sol (addSpoke, removeSpoke, forceRemoveSpoke, setRebalancer, reconcileTransit, acceptQuarantinedReport, rejectQuarantinedReport), SpokeAdminModule.sol (setAdapter, removeAdapter, setHub) -->

**Removed owner authority.** An earlier design, `adjustInTransitAssets`, permitted the owner to write `inTransitAssets` to an arbitrary value with no evidence, bound, or delay, an unbounded write directly into a value that determines share price. It was removed prior to release and replaced with `reconcileTransit`, which releases only a specific, already-tracked message id, by its exact tracked amount, and only after a seven day delay. The removal of the unbounded setter is itself a security property: no owner call in the current code can move `totalAssets()` by an arbitrary amount. <!-- verified: HubAdminModule.sol:reconcileTransit is the only function that adjusts inTransitAssets outside the normal send/confirm flow, and it is bounded to a specific tracked amount -->

**Rebalancer and agent authority.** `HUB`'s capital-movement functions, `sendToSpoke`, `recallFromSpoke`, `rebalance`, are gated to the single `REBALANCER` address. `Rebalancer.sol` gates `proposeAllocation`, `rebalance`, and `recallFromSpoke` to `onlyAuthorized`: the contract owner directly, or the `AgentConsumer` contract. `AgentConsumer` gates its own `proposeAllocation` forwarding to `onlyAgent`: its own owner, or a single designated `AGENT` wallet, the off-chain cron job's EOA. An allocation proposal therefore passes through two layers of access control before reaching the hub, and every proposal is checked against hard constraints (`AllocationMaths.validateAllocation`) regardless of origin. <!-- verified: HubMessagingModule.sol (onlyRebalancer modifier on sendToSpoke, recallFromSpoke, rebalance), Rebalancer.sol:_onlyAuthorized, AgentConsumer.sol modifier onlyAgent -->

**Spoke trust boundary.** A spoke is trusted to execute received instructions and to report its balance accurately; this trust is bounded on both counts. `isValidSpoke` gates which addresses the hub accepts `_ccipReceive` calls from: an address must be the currently registered spoke for its selector, and a past registrant no longer qualifies. A spoke's self-reported balance is not applied to `spokeBalances` directly; it passes through `_applyReportedBalance`'s upside-only sanity band, anchored to `netSentToSpoke`, the hub's own ledger of funds actually sent to that spoke. See [docs/resilience.md](resilience.md) for the band's full mechanics. <!-- verified: HubAdminModule.sol:isValidSpoke, HubMessagingModule.sol:_applyReportedBalance -->

**CCIP trust boundary.** Message authenticity from a legitimate router is verified entirely by the inherited `CCIPReceiver` base contract. In addition, both the hub and every spoke perform an explicit sender check, decoding `message.sender` and comparing it against the expected address: the hub checks against a registered spoke, the spoke checks against its stored `HUB`. A message passing the router check but originating from an unexpected contract on the source chain is rejected.

## Foundational invariants

The invariant test suite (`test/invariants/hub/`, `test/invariants/spoke/`) fuzzes call sequences against the live contracts and checks properties after every call: nineteen properties for the hub, nine for the spoke. Five are described here in prose, each with a note on how the suite enforces it.

1. **The accounting identity.** `totalAssets() == idle balance + inTransitAssets + sum of spokeBalances`. This identity underlies the fund location model in [docs/architecture.md](architecture.md). `invariant_accountingIdentity` checks it against live contract state after every fuzzed call sequence. <!-- verified: test/invariants/hub/hubInvariant.sol:invariant_accountingIdentity -->
2. **Reservations track live pending withdrawals exactly.** `reservedAssets` equals the sum of `reservedIdle` across every pending withdrawal, and the hub's escrowed share balance equals the sum of shares across those same entries. Two paired invariants enforce this: `invariant_reservedAssetsEqualsSumOfPendingReservedIdle` and `invariant_hubShareBalanceEqualsSumOfPendingShares`. <!-- verified: test/invariants/hub/hubInvariant.sol:invariant_reservedAssetsEqualsSumOfPendingReservedIdle, test/invariants/hub/hubInvariant.sol:invariant_hubShareBalanceEqualsSumOfPendingShares -->
3. **In-transit tracking does not desynchronize.** `inTransitAssets` never exceeds `totalAssets()`; within the invariant harness, where CCIP delivery is synchronous within the call that sends a message, it fully reconciles to zero between fuzzed calls, since every confirm lands before the next call in the sequence begins. A nonzero residual would indicate a leg's tracked amount was never released. <!-- verified: test/invariants/hub/hubInvariant.sol:invariant_inTransitAssetsBounded, test/invariants/hub/hubInvariant.sol:invariant_inTransitAssetsFullyReconciledBetweenCalls -->
4. **Share price does not fall below the 1:1 floor.** `convertToAssets(1e6)` never falls below `1e6 - 1` (one unit of rounding tolerance). This does not preclude fluctuation from yield or loss; it establishes that the vault never prices a share below the underlying asset it represents. <!-- verified: test/invariants/hub/hubInvariant.sol:invariant_sharePriceNeverDrops -->
5. **Every share is accounted for.** The hub's escrowed balance plus every tracked depositor's balance sums to exactly `totalSupply()`. Shares held in escrow during a pending withdrawal are included in this sum, since they are not burned until settlement. <!-- verified: test/invariants/hub/hubInvariant.sol:invariant_sumOfSharesEqualsTotalSupply -->

The remaining fourteen hub invariants and nine spoke invariants cover narrower properties, registry consistency, monotonic array growth, timestamp sanity, and are documented directly in the test files.

## Known limitations

| Limitation | Status |
|---|---|
| No owner-initiated manual pause, no separation between an automatic quarantine pause and a manual one | Open, deferred to v1.1. `_pause()`/`_unpause()` are called automatically only from within the sanity band logic; no owner entry point exists to pause or unpause outside that flow. <!-- verified: HubMessagingModule.sol:_applyReportedBalance is the only caller of _pause()/_unpause() anywhere in the Hub modules --> |
| `proposeAllocation` sizing semantics | Settled, not open. Allocations are sized as bps of `totalAssets()`, with a separate pre-check against currently unreserved idle that atomically fails the proposal before any CCIP send if it would not fit. <!-- verified: Rebalancer.sol:proposeAllocation --> |
| Single asset assumption | Accepted for v1. `ASSET` is one immutable `IERC20` per spoke, USDC in practice. Multi-asset support would require each adapter to manage its own token handling rather than the spoke assuming a single asset. <!-- verified: SpokeStorage.sol:ASSET --> |
| Preview functions do not reflect asynchronous settlement | Accepted for v1. `previewRedeem`/`previewWithdraw` are unmodified ERC4626 and compute as though redemption is always instant. When a withdrawal routes through Path 2 or Path 3, the eventual payout is repriced at settlement rather than at the preview call, the divergence an ERC-7540 style async vault would model explicitly with separate request and claim semantics. Meridian does not implement ERC-7540; this is a standard ERC4626 vault with an asynchronous settlement path. See [docs/withdrawals.md](withdrawals.md). <!-- verified: no override of previewWithdraw/previewRedeem/maxWithdraw/maxRedeem anywhere in src/hub/ --> |
| Path 2 freshness is a global, not per-withdrawal, condition | Accepted for v1. `_allSpokesFresh()` requires every active spoke to have reported within `MAX_STALENESS`, whether or not it is relevant to the specific withdrawal. A single spoke that stops reporting can stall every Path 2 withdrawal in the system, including those that would never have involved that spoke. <!-- verified: HubWithdrawalModule.sol:_allSpokesFresh, loops every active selector unconditionally --> |
| No timelock on the adapter registry | Accepted for v1, carried over from the original design reasoning. `setAdapter` and `removeAdapter` are both instant owner calls. `removeAdapter` being instant is intentional: an emergency circuit breaker must act faster than a compromised protocol can be further exploited. The same instant-call property on `setAdapter` is the actual tradeoff: a compromised owner key could point an adapter slot at a malicious contract immediately. Production deployment should use a multisig owner; a timelock specifically on `setAdapter`, while keeping `removeAdapter` instant, warrants consideration, without reintroducing the same latency on the emergency path. <!-- verified: SpokeAdminModule.sol:setAdapter, SpokeAdminModule.sol:removeAdapter, both onlyOwner with no delay --> |
