    FX-7: write pendingLegs before dispatching legs, not after (SHOULD)
    
    pendingLegs was written into the pending entry AFTER the leg-dispatch loop
    completed. In the synchronous CCIPLocalSimulator, a leg's confirm can arrive
    (and attempt settlement) WHILE the dispatch loop is still running for later
    legs — real CCIP always resolves dispatch and confirm-arrival in separate
    transactions, so this can't happen in production, but the sync test harness
    exposes it. If pendingLegs is still 0 (zero-initialized, not yet written)
    at the moment a leg arrives mid-loop, _handleWithdrawalCallback's
     guard is false and the decrement
    for that already-arrived leg is silently skipped. The trailing write then
    stomps pendingLegs back to the full original legCount, permanently
    overcounting outstanding legs by one per mid-loop arrival — which can never
    reach 0 again once the truly-last leg lands, permanently blocking FX-1's
    Path 3 settlement gate.
    
    Regression test confirms: with two legs planned (one real spoke, one mock
    that never resolves) and enough headroom that leg1's arrival alone doesn't
    trigger settlement, pendingLegs reads 2 (the full original count) instead
    of the correct 1 (only the still-outstanding leg2) after leg1 has already
    been credited — pre-fix.
    
    Fix: legCount is now computed during the existing dry-run pass (no new
    loop — same iteration, same haircut math, just also counting) and written
    into the PendingWithdrawal struct at creation time, before any leg is
    dispatched.

+/// @notice FX-7 regression — pendingLegs must be written into the pending entry BEFORE the
+///         leg-dispatch loop runs, not after.
+/// @dev The concrete manifestation: with the write AFTER the loop, a leg that arrives
+///      synchronously WHILE the dispatch loop is still running for later legs finds
+///      `pendingLegs` still at its zero-initialized value (the real value, legCount, isn't
+///      written until the whole loop finishes) — so `_handleWithdrawalCallback`'s
+///      `if (pendingLegs > 0) pendingLegs -= 1` guard is false and the decrement for that
+///      ALREADY-ARRIVED leg is silently skipped. Once the loop finally finishes and writes
+///      `pendingLegs = legCount` (the full original count, ignorant of the leg that already
+///      landed), the entry permanently OVERCOUNTS its outstanding legs by one per
+///      mid-loop arrival — which can never fully reach 0 again once the truly-last leg
+///      arrives, permanently blocking FX-1's Path 3 settlement gate. This only manifests in
+///      a synchronous harness (production CCIP always resolves dispatch and confirm-arrival
+///      in separate transactions, so the post-loop write always completes first) — but
+///      writing pendingLegs before dispatch makes the harness behavior match production
+///      ordering, which is the point of this fix.
